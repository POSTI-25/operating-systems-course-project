# Phase 5 — Execution and Evidence Design

Status: proposed for review. PRD.md is authoritative if this design conflicts with it.

## Intent and scope

Close the host-PC MVP by adding thin one-shot simulated execution, complete per-task decision records, the seven remaining §13 scenarios, four feature-flag variants of one Governor, a 32-run CSV report, and N1–N10 end-to-end evidence. No RTOS, process-control demo, new Gate predicate, Ledger dimension, utility term, external parser, GUI, or task recurrence. The repository remains private (§19). The approved lifecycle is one-shot: `period_ns` is metadata; invalidation pauses remaining execution; restoration resumes it after a fresh Gate pass.

## Approach selection

Use narrow hooks in the existing Governor. The mode-generation → Gate → Utility → commit path stays shared; an immutable variant policy selects modes, existing predicates, inputs, and event cadence. The Execution Adapter owns only progress state. The Logger serializes a fixed-size audit record produced by the Governor after a successful shadow-plan swap. A separate observer audits actual decisions against the full invariants for every variant. This keeps comparison scoring independent of the variant under test.

An external replay wrapper would leave the Governor nearly untouched but cannot reconstruct Gate eliminations, utility scores, or Ledger before/after accurately. Four scheduler implementations would duplicate and drift from the decision path, violating §14. Neither is selected.

## Cycle and execution lifecycle

At simulated time `t`, settle execution of the preceding interval before the new frame is handled. A task running from `last_resume_ns` accrues at most its `remaining_exec_ns`; if that remainder reaches zero at or before `t`, its completion timestamp is the exact due instant, not the later observation tick. Completion wins over a fault arriving at the same instant. Completion marks the task complete once, credits its selected mode's delivered value once, and releases rate and stock reservations. ENERGY remains held until the next fresh quality-OK SOC source timestamp, using the existing Ledger rule.

New commitments start running at commit time. An invalidation first accrues work until the invalidation instant, then freezes the remainder and releases the existing rate/stock reservation. Paused time earns no work. A successful restoration re-enters candidate generation, Gate, and Utility; it resumes the frozen remainder at the restoration instant. For the restored candidate, Gate completion-time and deadline-urgency calculations use the remaining duration via a temporary task view, not a new `Task` field. A mode change changes the value credited on eventual completion to the restored mode's value; it does not replay or erase elapsed work. To preserve the existing ENERGY invariant without inventing a partial-energy model, a restoration reserves the selected mode's full specified energy cost as a conservative bound on its remaining work. A still-held previous ENERGY reservation delays restoration until a fresh SOC budget clears it. A rejected task and a completed task never re-enter pending generation or revalidation.

The fixed-capacity `ExecutionState[SAGE_MAX_TASKS]` lives in `GovernorPlan` so an overrun discards execution and decision changes together with the Ledger shadow. The adapter accepts explicit simulated time and task/mode data; it has no clock, global mutable state, heap allocation, real work, or IPC knowledge. The prediction tracker continues to compare horizon forecasts with later observed telemetry; task completion is recorded as an execution outcome, not fabricated as a sensor sample. Scripted scenario telemetry is not modified by execution.

## LogRecord and deterministic logs

Each successful regular or fault cycle emits one `DECISION` record per task, including unchanged running/paused/completed tasks (`candidates=-`), plus a `PREDICTION` record when a horizon matures and a `TICK`/`SUMMARY` timing record in live runs. A decision record has stable field order:

`DECISION tick=<n> sim_ns=<t> trigger=<TICK|FAULT> task=<id> state_before=<PENDING|RUNNING|PAUSED|COMPLETE|REJECTED> candidates=<five mode/verdict/predicate/skip-mask tuples> selected=<mode|NONE> score=<six-decimal|NA> reason=<reason-token> ledger_before=<six dimension/capacity/reserve/committed/free tuples> ledger_after=<same> state_after=<state> invalidation=<record|NONE> restoration=<0|1> remaining_ns=<n> completed_ns=<n|NA> delivered_value=<n>`

The five candidate tuples appear in fixed `FULL|THROTTLED|DEGRADED|DEFERRED|REJECTED` order as `mode/verdict/failed_predicate/skip_mask`, where `verdict` is `PASS`, `ELIMINATED`, `FALLBACK_ONLY`, or `DISABLED_BY_VARIANT`; `failed_predicate` is the named first failing Gate predicate or `NONE`; and `skip_mask` is a hexadecimal mask of Gate predicates disabled by the variant. Only executing modes have a Gate verdict; fallback modes are `FALLBACK_ONLY` when enabled. Thus a skipped predicate is explicit even when another enabled predicate passes. The `GateFilterResult` supplies eliminations. The six Ledger tuples are `dimension:capacity:protected_reserve:committed:free`, in enum order, separated by `|`; SENSOR values are hexadecimal masks. The invalidation field is `task_id:cause_type:trigger_quantity:trigger_time_ns:original_mode:forecast_horizon_end:clear_count:K:upgraded_from_predicted`, or `NONE`. The reason-token vocabulary is `SELECTED`, `DEFERRED`, `REJECTED`, `EMERGENCY_SAFE_MODE`, `RESTORE_BLOCKED_GATE`, `RESTORE_BLOCKED_BUDGET`, `ALREADY_RUNNING`, `PAUSED`, and `COMPLETED`; an `OVERRUN` line reports the retained plan without pretending tentative decisions committed. `tick` is the count of completed regular tick intervals at `sim_ns`; a fault event between ticks shares the previous tick number and is distinguished by `trigger=FAULT`. Logging occurs only after shadow commit, so discarded decisions cannot leak into evidence.

The Logger uses explicit records and `FILE *`; it does not infer decisions from final commitments. It prints only deterministic fields into the scenario golden stream. Wall-clock CPU, jitter, calibration cap, and modeled self-cost are emitted separately and are excluded from exact golden diffs. The existing Phase 1 `golden/normal_orbit.expected` telemetry fixture remains intact. Eight new `golden/<scenario>.decisions.expected` files cover full-variant decision traces, including `normal_orbit`.

## Variant policy and shared engine

One immutable `GovernorVariant` configuration controls allowed modes, enabled existing Gate predicates, enabled utility terms, prediction inputs, Ledger admission dimensions, revalidation inputs, and fault-event cadence. The default is SAGE-RT full. The policy does not define new Gate predicates, Ledger dimensions, or utility terms. Disabled checks are logged explicitly. An unchecked baseline admission records actual demand in the same Ledger reservation structure without using it to veto selection; its potentially negative free capacity is evidence, not permission in the full variant. Revalidation/overcommit shedding uses only predicates enabled for that variant. The independent safety auditor always uses all full invariants and observed telemetry.

| Variant | Exact behavior |
|---|---|
| Fixed-priority/EDF | Tasks ordered by criticality class, then earliest absolute deadline, then ID; `FULL` only; no Gate predicate, prediction, cross-resource admission check, or event-triggered replan. It still records demand and completes work through the shared adapter. |
| GomX-3-style | `FULL` or `DEFERRED`; current SOC, solar input, and eclipse are its sensor inputs; SOC-floor and deadline checks only; ENERGY-only admission; no thermal/fault check or fault-interrupt cycle. The existing Ledger harvest argument receives nonnegative `solar_input_mW × H / 10^9` mJ only outside eclipse, with checked integer arithmetic. It does not also apply Holt SOC trend, avoiding harvest double counting. Class 0 still follows the PRD's no-defer rule and enters the existing zero-demand emergency schedule if its only executing mode fails. |
| Ranjbar-style | Fault flags, criticality, and primary-subsystem temperature are safety inputs; thermal, protected-residual, and deadline checks remain; SOC-floor and solar/battery model are disabled for admission and utility. Non-energy Ledger dimensions remain active for resource feasibility. Fault events may cause immediate cycles. |
| SAGE-RT | Existing Holt forecast, all five modes, all four Gate predicates, all Ledger dimensions, full Utility, full Revalidation, and immediate fault cycles. |

The baseline names are approximate feature ablations, not claims of fidelity to published spacecraft implementations. The report labels them “-style”. Feature flags cannot alter the independent audit. The final score uses identical scenarios, scenario duration, task sets, and audit formulas. The test hook that injects self-cost remains test-only and is not a baseline feature.

## Scenario catalog and replay

Use the existing §13 grammar without new directives. Keep `normal_orbit.scn` unchanged. Add seven compact files whose initial channels are complete and whose task profiles specify all three modes, even where a variant masks modes:

1. `low_soc_eclipse.scn`: SOC near floor, orbit eclipse transition, a payload whose full cost is unsafe and a class-0 task competing for energy.
2. `high_thermal_load.scn`: primary-subsystem temperature rises toward a mode-specific thermal ceiling; lower mode survives when full does not.
3. `sudden_fault.scn`: fault bit escalates between regular ticks for a running task, making the immediate-cycle path observable.
4. `communication_blackout.scn`: comm capacity drops to zero while a comm-dependent task is pending/running; non-comm alternatives remain visible.
5. `competing_payload_tasks.scn`: tasks compete for CPU, memory, sensor, and ENERGY; priority and Ledger residuals are visible.
6. `compound_stress.scn`: ADCS/reaction-wheel fault during eclipse, low SOC, ADCS near thermal ceiling, queued payloads, and a later protected-capacity shortfall that exercises Emergency Safe Mode. This is the primary N3/N7/N8/N10 evidence run.
7. `false_alarm_restoration.scn`: a fresh trend forecast triggers `PREDICTED_RISK`; actual telemetry remains safe through its horizon; the task restores after a Gate re-pass and resumes remaining execution.

The virtual replay runner feeds the same ordered frame and fault events into the Governor that the fork/pipe path uses, but does not wait in real time. It advances regular ticks and immediate fault cycles at their simulated timestamps, including coincident-event ordering from §13. The decision golden file is generated from this replay, reviewed, and then treated as expected output, not regenerated as part of `make test`. The live fork/pipe path remains tested separately. `make test` diffs all eight decision goldens and the original normal-orbit telemetry golden.

## Metrics and fair audit rules

`docs/phase5_metrics.csv` has one row per `(scenario, variant)` and `docs/phase5_evidence.md` holds the aggregate/compound-stress comparison and N1–N10 index. The CSV schema is `scenario,variant,task_count,critical_task_count,completed_count,critical_completed_count,deadline_misses,rejected_by_design,mission_work_completed,completion_ratio,critical_completion_ratio,safety_violations,safety_task_instants,safety_violation_rate,protected_resource_violations,energy_survival_time_ns,energy_survival_censored,recovery_latency_ns,recovery_latency_censored,replan_count,cpu_time_ns,self_cost_cap_ns,modeled_self_energy_mJ,tick_jitter_ns,prediction_abs_error`. Every count is defined over one-shot tasks. `deadline_misses` counts non-rejected tasks whose completion did not occur by their absolute deadline (including still-pending/paused tasks once their deadline passes within the scenario); `rejected_by_design` is separate and excluded from that count. `mission_work_completed` sums delivered value only on completion. `completion_ratio` and `critical_completion_ratio` divide completed tasks by all tasks and by all class-0 tasks respectively; an absent class-0 denominator is `NA`, not 100%.

At every distinct simulated decision instant, an independent full-policy audit checks each actually running task against observed SOC, thermal, deadline, and aggregate Ledger/protected-reserve feasibility. `safety_violations` counts failing task-predicate observations; `protected_resource_violations` is the subset attributable to protected-reserve access or physical capacity breach. Counts are reported with task-instant denominators so variants with different run durations are comparable. A task can fail more than one predicate at one instant, and the CSV exposes both count and rate. No variant is credited for silently skipping a check.

`energy_survival_time_ns` is the first observed SOC below the scenario floor, or the scenario duration if no crossing is observed, with a censor flag. Because telemetry is scripted and execution does not feed back into it, this metric is exogenous and may be identical across variants; the report must not imply a causal energy-survival improvement. `recovery_latency_ns` is elapsed simulated time from each fault escalation to the first corresponding replan or safe-mode transition; a variant that never reacts is marked censored, not assigned zero latency. `replan_count` counts actual invalidation/restoration/emergency transitions. CPU overhead and cap come from `CLOCK_PROCESS_CPUTIME_ID`; modeled energy uses the existing explicit 2.0 W assumption; jitter is measured only in paced live runs and labeled `NA` in instantaneous virtual replay. Prediction error uses matched forecast/actual horizons; a non-predictive variant reports `NA` rather than a fabricated zero.

The report never tunes fixtures or suppresses rows to achieve the requested comparison. It summarizes SAGE-RT against each variant per category and compound stress. If full does not have fewer audited safety violations or higher critical completion than a comparator, that result is reported as a finding; the Phase 5 status is not marked complete until the user decides whether the unmet exit criterion is acceptable or changes the scope.

## Verification and evidence mapping

Develop with red/green tests in this order: adapter pause/resume/completion and resource lifecycle; Logger serialization and complete InvalidationRecord; variant masking and independent audit; virtual replay/event ordering; seven scenarios with reviewed golden traces; 32-run CSV metrics; N1–N10 traceability; strict build, full tests, sanitizer. Tests include exact completion/fault collision, overrun-discarded execution/logs, same-time fault vs tick, malformed/overflow-safe metrics, missing telemetry audit, and no recurrence. No scenario is added beyond the required eight.

The final traceability index names evidence rather than introducing mechanisms: N1 unsafe-high-utility Gate trace plus unit test; N2 comm failure with battery pass; N3 compound protected-violation metric; N4 false-alarm restore log; N5 mode distribution vs GomX; N6 overhead/cap line; N7 fault recovery latency vs tick-only GomX; N8 thermal/fault ablation rows; N9 existing prediction A/B plus an end-to-end low-SOC trace; N10 compound Emergency Safe Mode record. A claim with missing evidence remains explicitly unresolved. Update PRD §16/§18 and the top-level status only after `make`, `make test`, and `make sanitize` pass and the report is inspected.

## Design-review choices to confirm

The variant table, audit denominators, and no-telemetry-feedback rule above are the proposed precise interpretations of terse PRD §14 language. They are part of this design review, not hidden implementation assumptions. The requested “SAGE-RT wins” comparison is a measured hypothesis, not a fixture-generation target. No implementation begins until this spec is approved and the subsequent implementation plan is reviewed.
